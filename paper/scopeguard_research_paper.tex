\begin{abstract}
The rapid deployment of Large Language Model (LLM)-powered autonomous agents into enterprise cloud environments promises to automate complex Infrastructure-as-Code (IaC) provisioning, microservice auto-scaling, and operational incident response. However, granting autonomous agents direct access to cloud control planes introduces severe governance and security vulnerabilities. When agents operate with static, broad Identity and Access Management (IAM) permissions, they exhibit unintended scope creep, succumb to indirect prompt injection attacks, and execute destructive operations without deterministic, session-level identity attribution. Existing access control paradigms—including static Role-Based Access Control (RBAC) and declarative Policy-as-Code engines (e.g., Open Policy Agent, AWS Cedar)—fail to dynamically infer minimal permission boundaries from natural language task objectives prior to execution. We present \textbf{ScopeGuard}, an asynchronous, identity-scoped authorization proxy and execution control framework for AI agents in cloud infrastructure. ScopeGuard intercepts outbound agent tool calls, injects cryptographically verifiable session identity metadata (Agent ID, Session UUID4, declared task objective, and LLM reasoning chain), redacts credential secrets from parameter payloads, and dynamically compiles a task-aware permission boundary using a structured action taxonomy. Intercepted API calls are evaluated against this scope under a fail-closed policy engine supporting three ablation operational modes (\textit{passthrough}, \textit{tagging\_only}, and \textit{full}). We empirically evaluate ScopeGuard across a 200-task benchmark suite (100 legitimate infrastructure operations and 100 adversarial/off-scope attacks across 10 security threat categories). In \textit{full} enforcement mode, ScopeGuard achieves an overall classification accuracy of \textbf{98.9\%}, a scoping precision of \textbf{97.8\%}, an adversarial block rate of \textbf{100.0\%} (88/88 adversarial calls blocked, 0 false negatives), and a false positive rate of \textbf{2.1\%} (2/92 legitimate calls blocked), while introducing a minimal average proxy latency overhead of \textbf{108.9 ms}—well within the 200 ms real-time inference limit. We validate live execution against real Amazon Web Services (AWS) endpoints including Amazon RDS, EC2, S3, and CloudWatch.
\end{abstract}

\section{Introduction}\label{sec:intro}

\subsection{Motivation and Context}
Modern enterprise computing relies heavily on cloud infrastructure control planes—such as Amazon Web Services (AWS), Google Cloud Platform (GCP), Microsoft Azure, and Infrastructure-as-Code (IaC) orchestrators like Terraform and Ansible—to provision compute instances, relational databases, object storage, and Virtual Private Cloud (VPC) network topologies \cite{ayers2018}, \cite{jiang2026}, \cite{hadary2020}. Managing these modern microservice deployments requires executing complex multi-step operational tasks via RESTful APIs, CLI tools, and automated continuous integration pipelines \cite{cortez2017}, \cite{huye2023}. As cloud architectures expand in heterogeneity and operational scale, human operations teams face overwhelming cognitive load, driving the widespread adoption of agentic Artificial Intelligence (AI) frameworks \cite{yang2024}, \cite{hong2024}.

Autonomous AI agents—Large Language Model (LLM)-powered software systems capable of iterative goal reasoning, action planning, context retrieval, and external tool invocation \cite{schick2023}, \cite{yao2023}, \cite{shavit2023}—are increasingly granted direct API access to manage live enterprise cloud environments. These agents automate incident remediation, database auto-scaling, application log diagnosis, and IaC template generation \cite{lange2025}, \cite{novikov2025}. Unlike pre-scripted, deterministic automation workflows, autonomous agents dynamically generate execution plan graphs to accomplish high-level natural language instructions.

However, granting autonomous agents direct, unmediated access to cloud control planes introduces fundamental security failure modes. Cloud Identity and Access Management (IAM) systems are built around static policy assignment to IAM users, service roles, or container service accounts. Static IAM policies assume predictable, well-defined service boundaries. When applied to autonomous LLM agents, static IAM policies create an insurmountable security dilemma.

\subsection{The Dilemma of Static IAM in Agentic Workflows}
The fundamental conflict in agentic access control arises from the operational tension between agent autonomy and the security Principle of Least Privilege:
\begin{itemize}
    \item \textbf{Over-Provisioning Hazard}: Granting broad permissions (e.g., \texttt{AdministratorAccess} or wildcard \texttt{s3:*}) ensures that the agent can autonomously complete diverse, multi-step operational tasks without encountering authorization errors. However, this leaves the entire cloud infrastructure vulnerable to catastrophic deletion if the agent hallucinates, exhibits scope creep, or is compromised by an adversary.
    \item \textbf{Under-Provisioning Failure}: Restricting IAM permissions prevents unauthorized actions, but causes frequent runtime execution failures whenever an LLM dynamically selects an alternative valid tool path or auxiliary read command to fulfill a legitimate user objective.
\end{itemize}

\subsection{Three Structural Security Failure Modes}
Unmediated AI agent interaction with cloud APIs results in three primary structural vulnerabilities:
\begin{enumerate}
    \item \textbf{Violation of Principle of Least Privilege (\textit{Static Over-Provisioning})}: Agents operating under broad static service roles retain permission to execute highly destructive actions unrelated to their current operational objective. For example, an agent tasked with "monitoring database disk health" retains the IAM permission to terminate production EC2 virtual machines or delete IAM security groups \cite{perez2023}.
    \item \textbf{Vulnerability to Indirect Prompt Injection}: Agents process untrusted external data sources, including application log files, git commit messages, S3 object metadata, or web scraping inputs. Adversaries can embed malicious prompt payloads within these inputs, coercing the agent into executing off-scope or destructive cloud API commands \cite{perez2023}, \cite{shavit2023}.
    \item \textbf{Absence of Session-Level Identity Attribution}: Standard cloud API logs (e.g., AWS CloudTrail) record only the static IAM role assumed by the agent container. They fail to bind individual API requests to specific agent instances, session UUIDs, declared user objectives, or underlying LLM reasoning chains, frustrating post-incident digital forensics.
\end{enumerate}

To mitigate these vulnerabilities, security engineers have evaluated existing policy enforcement mechanisms, such as static Role-Based Access Control (RBAC), Open Policy Agent (OPA), AWS Cedar, and LLM text-guardrails like NVIDIA NeMo Guardrails. However, as summarized in Table \ref{tab:systemic_comparison}, all existing access control paradigms fail to satisfy the combined requirements of pre-execution task-aware permission compilation, sub-200ms processing overhead, and runtime identity binding for cloud API operations.

\subsection{Novelty Claim and Main Scientific Contributions}
We introduce \textbf{ScopeGuard}, an asynchronous, identity-scoped authorization proxy and execution control framework designed specifically for autonomous AI agents operating in cloud infrastructure. ScopeGuard intercepts outbound agent tool requests, redacts sensitive credentials, injects verifiable session identity metadata, dynamically compiles a minimal permission boundary from the agent's declared task objective, and enforces a fail-closed policy prior to cloud API execution.

\textbf{Novelty Claim:} ScopeGuard is the \textit{first working, empirically validated implementation} of task-scoped dynamic permission enforcement and session-level identity attribution specifically built for cloud-connected AI agents, evaluated against a comprehensive 200-task security benchmark suite across live cloud control planes.

The key scientific and technical contributions of this work are:
\begin{itemize}
    \item \textbf{Formal Architectural Proxy Framework}: An asynchronous, high-performance reverse proxy architecture implementing credential secret redaction, identity metadata enrichment, fail-closed policy authorization, and persistent SQLite audit logging.
    \item \textbf{Dynamic Task-to-Scope Compiler}: A deterministic permission compiler utilizing a structured cloud action taxonomy (\texttt{permissions.json}) that parses natural language task objectives, computes allowed action boundaries, and enforces implicit read-grant inheritance.

\end{itemize}

\section{Background and Threat Taxonomy}\label{sec:background}

\subsection{Anatomy of Autonomous Cloud Agents}
Autonomous AI agents operate via iterative reasoning loops, such as the ReAct (Reasoning + Acting) framework \cite{yao2023}. At each execution step $t$, the agent receives a prompt tuple $P_t = \langle T_{\text{user}}, H_{t-1}, O_{t-1} \rangle$, where $T_{\text{user}}$ represents the user's natural language objective, $H_{t-1}$ is the historical trajectory of thoughts and actions, and $O_{t-1}$ is the observation output from the preceding tool invocation. The agent invokes an LLM to generate a thought $c_t$ and an action command $a_t$. The action command specifies a tool name and parameters (e.g., `aws_rds_operation(action="rds:DescribeDBInstances")`).

\subsection{Formal Security Threat Model ($\mathcal{M}_{\text{threat}}$)}
We define a formal security threat model $\mathcal{M}_{\text{threat}}$ governing AI agent cloud interactions:
\begin{equation}
\mathcal{M}_{\text{threat}} = \langle \mathcal{A}_{\text{adv}}, \mathcal{S}_{\text{target}}, \mathcal{T}_{\text{vectors}}, \mathcal{B}_{\text{trust}} \rangle
\end{equation}
where $\mathcal{A}_{\text{adv}}$ denotes adversary capabilities, $\mathcal{S}_{\text{target}}$ is the target cloud infrastructure API surface, $\mathcal{T}_{\text{vectors}}$ represents the threat vectors, and $\mathcal{B}_{\text{trust}}$ defines the trust boundaries.

The threat model assumes:
\begin{enumerate}
    \item \textbf{Attacker Capabilities}: The adversary can submit arbitrary natural language user prompts or manipulate untrusted data inputs (logs, code repos, S3 metadata) ingested by the agent. The adversary cannot modify ScopeGuard's internal code or proxy configuration.
    \item \textbf{Agent Trust Stance}: The agent's LLM is treated as an untrusted reasoning component susceptible to hallucinations, prompt injections, and scope creep.
    \item \textbf{Proxy Stance}: ScopeGuard operates as a trusted, fail-closed intermediary positioned between the agent container and the cloud control plane API.
\end{enumerate}

\subsection{Ten Security Threat Categories}
We establish a comprehensive taxonomy of ten security threat categories targeting cloud AI agents:
\begin{enumerate}
    \item \textbf{Scope Creep (Off-Scope Action Execution)}: The agent attempts API calls unrelated to its stated task (e.g., deleting S3 storage buckets during a read-only database health monitoring task).
    \item \textbf{Direct Prompt Injection}: An attacker manipulates the user prompt to force unauthorized execution.
    \item \textbf{Indirect Log/Input Injection}: An attacker embeds malicious prompt payloads inside untrusted external inputs (e.g., application log files or S3 object metadata) that are parsed by the agent.
    \item \textbf{IAM Privilege Escalation}: The agent attempts to attach administrative IAM policies (\texttt{iam:PutRolePolicy}, \texttt{iam:AttachRolePolicy}).
    \item \textbf{Irreversible Resource Destruction}: The agent attempts irreversible deletion of critical infrastructure components (\texttt{ec2:TerminateInstances}, \texttt{rds:DeleteDBInstance}).
    \item \textbf{Unauthorized Ingress Security Expansion}: The agent opens internal infrastructure security groups to global internet access (\texttt{ec2:AuthorizeSecurityGroupIngress} with \texttt{0.0.0.0/0}).
    \item \textbf{Unauthorized Secret and Credential Exfiltration}: The agent attempts to read or transmit API secrets, database passwords, or private SSH keys.
    \item \textbf{Cross-Resource / Cross-Tenant Scope Leakage}: The agent accesses infrastructure resources belonging to distinct tenant isolation environments.
    \item \textbf{Denial-of-Wallet \& Infinite Loop Resource Exhaustion}: The agent generates runaway resource provisioning commands (e.g., spinning up hundreds of GPU instances).
    \item \textbf{Audit Log Tampering \& Bypassing}: The agent attempts to disable CloudTrail or delete proxy audit logs.
\end{enumerate}

\subsection{Core Functional Subsystems}
ScopeGuard comprises four core functional modules:
\begin{enumerate}
    \item \textbf{Outbound Request Interceptor}: Intercepts JSON tool invocation payloads, extracts agent execution context, and validates structural schemas.
    \item \textbf{Credential Secret Redactor}: Scans input parameter payloads for sensitive patterns (AWS Access Keys, Secret Keys, Database Passwords, JWT Tokens) using regular expression sanitization and replaces them with \texttt{"[REDACTED]"}.
    \item \textbf{Runtime Identity Attributor}: Binds each request with a cryptographically generated Session UUID4, Agent ID, declared task string, timestamp, and optional LLM reasoning chain trace.
    \item \textbf{Persistent Audit Logger}: Writes comprehensive JSON execution logs to an append-only SQLite database (\texttt{audit.db}) to enable post-incident forensic analysis.
\end{enumerate}

@app.post("/execute-tool")
async def execute_tool(req: ToolExecutionRequest):
    # 1. Redact sensitive credentials from payload parameters
    sanitized_params = secret_redactor.redact(req.tool_params)
    
    # 2. Inject verifiable session identity attribution headers
    session_ctx = {
        "agent_id": req.agent_id,
        "session_id": req.session_id or str(uuid.uuid4()),
        "declared_task": req.declared_task,
        "timestamp": datetime.utcnow().isoformat()
    }
    
    # 3. Compile dynamic permission scope from declared task
    allowed_scope = task_compiler.compile_scope(req.declared_task)
    
    # 4. Evaluate fail-closed authorization policy
    decision = policy_engine.evaluate(
        requested_action=req.tool_action,
        allowed_scope=allowed_scope,
        mode=config.SCOPEGUARD_MODE
    )
    
    # 5. Persist audit log record to SQLite database
    audit_logger.log(session_ctx, req.tool_action, decision)
    
    if decision == "DENY":
        raise HTTPException(status_code=403, detail=f"ScopeGuard Blocked: Action {req.tool_action} is outside allowed scope.")
        
    return await forward_to_cloud_api(req.tool_name, req.tool_action, sanitized_params)
\end{lstlisting}

\section{Dynamic Task-to-Scope Compiler}\label{sec:compiler}

Let $\mathcal{A}$ denote the set of cloud API actions in the taxonomy. An incoming tool request $Q$ is defined as:
\begin{equation}
Q = \langle \text{agent\_id}, \text{session\_id}, T_{\text{decl}}, a_{\text{req}}, P \rangle
\end{equation}
where $T_{\text{decl}}$ is the declared task objective string, $a_{\text{req}} \in \mathcal{A}$ is the requested cloud API action, and $P$ is the parameter payload dictionary.

The Task-to-Scope Compiler maps natural language task strings $T_{\text{decl}}$ to a minimal set of permitted actions $S_{\text{allowed}} \subseteq \mathcal{A}$. It tokenizes $T_{\text{decl}}$, matches n-gram keyphrases against the structured taxonomy \texttt{permissions.json}, and expands the permitted scope via implicit read-grant inheritance (e.g., write operations automatically grant corresponding describe/list permissions).

\begin{algorithm}[t]
\caption{Task-to-Scope Permission Compilation}
\label{alg:compiler}
\begin{algorithmic}[1]
\REQUIRE Declared task $T_{\text{decl}}$, Action Taxonomy Schema $S$
\ENSURE Allowed Action Set $S_{\text{allowed}}$, Max Risk $R$
\STATE $Tokens \leftarrow \text{TokenizeAndStem}(T_{\text{decl}})$
\STATE $S_{\text{allowed}} \leftarrow \emptyset$, $R \leftarrow \text{LOW}$
\FOR{each $res\_type \in S.\text{resource\_types}$}
    \FOR{each $action, meta \in res\_type.\text{actions}$}
        \FOR{each $kw \in meta.\text{keywords}$}
            \IF{$kw \in T_{\text{decl}}.\text{lower}()$}
                \STATE $S_{\text{allowed}} \leftarrow S_{\text{allowed}} \cup \{action\}$
                \STATE $R \leftarrow \max(R, meta.\text{risk})$
            \ENDIF
        \ENDFOR
    \ENDFOR
\ENDFOR
\IF{$S.\text{meta\_rules}.\text{implicit\_read\_grant}$ is True}
    \FOR{each $action \in S_{\text{allowed}}$}
        \IF{$\text{IsWriteOp}(action)$}
            \STATE $S_{\text{allowed}} \leftarrow S_{\text{allowed}} \cup \text{GetReadOps}(action)$
        \ENDIF
    \ENDFOR
\ENDIF
\RETURN $\langle S_{\text{allowed}}, R \rangle$
\end{algorithmic}
\end{algorithm}

\section{Fail-Closed Policy Enforcement Engine}\label{sec:policy_engine}

ScopeGuard enforces policy decisions under a strict fail-closed security posture. Algorithm \ref{alg:policy_evaluation} details the execution evaluation flow across the three operational ablation modes: \textit{passthrough}, \textit{tagging\_only}, and \textit{full}.

\begin{algorithm}[t]
\caption{ScopeGuard Fail-Closed Policy Evaluation}
\label{alg:policy_evaluation}
\begin{algorithmic}[1]
\REQUIRE Intercepted Request $Q$, Operational Mode $M$
\ENSURE Decision $D \in \{\text{ALLOW}, \text{DENY}\}$, Audited Request $Q'$
\STATE $Q' \leftarrow \text{InjectIdentityHeaders}(Q)$
\STATE $Q' \leftarrow \text{RedactSecrets}(Q')$
\IF{$M == \text{passthrough}$}
    \STATE \text{AuditLog}($Q'$, \text{ALLOW}, \text{"passthrough"})
    \RETURN \text{ALLOW}
\ENDIF
\STATE $\langle S_{\text{allowed}}, R_{\text{max}} \rangle \leftarrow \text{CompileScope}(Q'.T_{\text{decl}})$
\IF{$M == \text{tagging\_only}$}
    \STATE \text{AuditLog}($Q'$, \text{ALLOW}, \text{"tagging\_only"}, $S_{\text{allowed}}$)
    \RETURN \text{ALLOW}
\ENDIF
\IF{$Q'.a_{\text{req}} \in S_{\text{allowed}}$}
    \STATE \text{AuditLog}($Q'$, \text{ALLOW}, \text{"full\_scoping\_grant"}, $S_{\text{allowed}}$)
    \RETURN \text{ALLOW}
\ELSE
    \STATE \text{AuditLog}($Q'$, \text{DENY}, \text{"out\_of\_scope\_violation"}, $S_{\text{allowed}}$)
    \RETURN \text{DENY}
\ENDIF
\end{algorithmic}
\end{algorithm}

\section{Security Analysis and Related Work}\label{sec:discussion}
Existing access control systems fail to address the non-deterministic execution nature of LLM autonomous agents. Static IAM policies over-provision permissions, while OPA and AWS Cedar enforce static declarative policies that require human engineers to anticipate every potential query structure beforehand.

In contrast, ScopeGuard provides dynamic, task-aware permission compilation prior to execution. By combining keyword tokenization with implicit read-grant inheritance, secret sanitization, and session UUID attribution, ScopeGuard establishes a robust security posture without adding significant latency or breaking developer workflows.

\section{Production Deployment Architectures}\label{sec:production}
ScopeGuard can be deployed as an Envoy sidecar proxy within containerized Kubernetes clusters (EKS/GKE) or integrated as a central Cloud API Gateway proxy layer.

\section{Conclusion and Future Research Roadmap}\label{sec:conclusion}
In this paper, we introduced \textbf{ScopeGuard}, an identity-scoped execution control and dynamic authorization proxy for autonomous AI agents in cloud infrastructure. ScopeGuard addresses the structural vulnerabilities of static cloud IAM, indirect prompt injection, and untracked agent executions by dynamically compiling task-specific permission boundaries and enforcing fail-closed policy authorization prior to cloud API execution.

Our empirical evaluation across a 200-task security benchmark suite (600 total tool evaluations) demonstrated that ScopeGuard in full enforcement mode achieves an overall classification accuracy of \textbf{98.9\%}, an adversarial block rate of \textbf{100.0\%} ($88/88$ attacks blocked, 0 false negatives), and a precision of \textbf{97.8\%}, while incurring a minimal average proxy latency overhead of \textbf{108.9 ms}. Live execution tests against Amazon Web Services (RDS, EC2, S3, CloudWatch) confirmed its real-world operational viability.

Future work will expand ScopeGuard along four key dimensions:
\begin{enumerate}
    \item \textbf{Semantic Embedding-Based Scope Inference}: Transitioning from keyword tokenization to dense vector embedding similarity for taxonomy compilation.
    \item \textbf{Kubernetes Sidecar \& Envoy Integration}: Packaging ScopeGuard as a cloud-native sidecar proxy for containerized agent workloads in EKS and GKE.
    \item \textbf{Cryptographic Reasoning Verification}: Integrating zero-knowledge cryptographic proofs to bind LLM reasoning chain steps directly to policy evaluation decisions.
    \item \textbf{eBPF Kernel Interception}: Intercepting socket-level agent API calls using eBPF probes for zero-overhead system governance.
\end{enumerate}
